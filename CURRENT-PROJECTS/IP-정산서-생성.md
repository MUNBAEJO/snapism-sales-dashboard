# IP 정산서 자동 생성 (스내피즘 · 포토이즘)

실무자가 **지라 티켓번호를 입력하면** 우리 매출 데이터로 **정산서 PDF를 직접 생성**하는 페이지.
지금은 담당자가 수작업으로 만들어 배포하고 있고, 대시보드는 조회만 된다.

## 현재 상태
- **Owner:** 조문배 (기획 · 개발 · 운영)
- **상태:** 기획 완료 (2026-07-29) — 구현 착수 전
- **연결 페이지:** 매출 대시보드에서 링크로 진입하는 **별도 페이지**(무거워지지 않게 분리)
- **기존 자산:** `C:\Users\Administrator\ip-settlement-automation` (Node, 프레임수 엑셀 생성 — 현행 파트너 발송본)
- **참고 디자인:** `정산서_조문배_2026-06.pdf` (투자 정산서 — 형식·레이아웃만 참고)

## 목적
1. **내가 만들어주지 않고 실무자가 직접** 정산서를 만든다 → 그래서 정확성이 최우선
2. **스내피즘 전용 → 포토이즘까지 확대** (브랜드 축 신설)
3. 추후 **메일 발송**까지

## 실측 현황 (2026-06 기준)

### 티켓 귀속 품질 — **이 프로젝트의 핵심 난제**
| 브랜드 | 정산대상 매출 | 티켓 1장에 정확히 귀속 |
|---|--:|--:|
| 포토이즘 (아티스트·캐릭터·PICK) | ₩6,160,343,965 | **44.9%** |
| 스내피즘 | ₩292,699,164 | **31.8%** |

나머지는 1:N(후보 여러 개) · N:1(한 티켓에 여러 타이틀) · 미연결.
**"연결률 93~98%"는 아무 티켓이나 하나 붙었다는 뜻**이지 맞는 티켓이라는 뜻이 아니다.

### 반드시 피해야 할 함정
- **빈 타이틀 ₩6,697,920,204(오리지널)이 `CANDIP-26514` 한 장에 통째로 붙는다.**
  `normalize_title("") == ""` 이고 캐시에도 `""`로 정규화되는 티켓이 14개 있어서 생긴다.
  → 정산 대상을 아티스트·캐릭터·PICK으로 한정하면 회피되지만, **빈 타이틀 가드를 반드시 넣는다.**
- **타이 브레이커가 없다** (`title_runs.py:203`). 기간이 완전히 같은 후보(TREASURE 3장, tripleS 3장, 정용화·DAY6 각 2장)는
  **캐시 파일 줄 순서로 승자가 정해진다 → 재크롤하면 정산 결과가 바뀐다.** 정산에 그대로 쓰면 안 됨.
- **코르티스 ₩8.8억은 후보 티켓이 8장.** 사람이 확정해야 한다.
- **환율 미적용 시 순위가 뒤집힌다** (IDR·VND). 반드시 통화별 환산.
- `startdate/duedate`는 **계약기간이 아니라 송출·검수 일정**이다. 계약기간으로 쓰면 안 됨.

### 요율(RS) 입력률 — 지라 직접 조회 실측
| 브랜드 | 티켓 수 | RS 입력됨 |
|---|--:|--:|
| 스내피즘 | 362 | 117건 (32.3%) |
| 포토이즘 | 2,779 | 223건 (8.0%) |

포토이즘에도 값은 있다(예: `CANDIP-32374` 소속사 0.3 / 대행사 0.1).
**JQL 브랜드 조건만 넓히면 붙는다.** 다만 입력률이 낮아 화면 입력 경로가 필수.

### 정산서 PDF 구성 — 샘플 검증 완료 (2026-07-29)
**Playwright chromium `page.pdf()`** + HTML/CSS. 톤앤매너는 **대시보드와 동일**
(Pretendard, `--brand:#4f46e5`, `.kpi` 카드, `.ntbl` 표 + 비중 막대).
실물 샘플: `reports/정산서_TREASURE_2026-06_{소속사|대행사}.pdf`

**수취처마다 파일 1개**(소속사 / 대행사) — 요율이 다르므로 분리 발행.

```
1p 요약
  [재발행 배지] 정정본 vN + 발행사유       ← 스냅샷 잠금·재발행 이력
  IP명 / '{정산 시작} ~ {정산 종료} 정산분' / 발행일
  판매기간(지라) {start} ~ {due}  [진행 중]
  ▶ {수취처} 정산액 (큰 숫자) · 정산기준액 × 요율 N%
  브랜드별 요약 표 — 브랜드 | 오픈·매출발생 국가 | 프레임수·건수 | 매출 | 정산액 | 합계
    └ 단위가 다르므로 셀에 '프레임' / '건' 을 붙이고 **합계 칸은 비운다**
  최종 정산액 = 포토이즘 + 스내피즘
  ※ 각주 (4줄까지만)

2p 📸 포토이즘 / 3p 📊 스내피즘   ← 브랜드마다 한 장씩
  브랜드 헤더 + 판매기간 + 오픈 N개국 중 매출발생 M개국
  🍩 국가별 매출 비중 도넛           ← 상단. 멤버별 비중은 넣지 않음
  🌏 국가별 내역 표 (매출 0인 오픈 국가도 '매출 없음' 배지로 표기)

4p 📸 포토이즘 국가 × 멤버 프레임수   ← 27행
5p 📊 스내피즘 국가 × 멤버 건수 + 산출 방식   ← 8행
6p 국가별 단가 — **한 표에 두 브랜드를 열로** (국가 | 통화 | 포토이즘 | 스내피즘)
```
> **단가표는 반드시 한 표로 합친다.** 브랜드별로 쪼개면 27행짜리가 페이지 경계에 걸려
> '헤더 + 1행'만 남고 잘린다. 스내피즘 국가는 포토이즘 국가의 부분집합이라 열로 붙으며,
> 국가 순서는 2p 국가별 내역과 동일하게 맞춘다.

**표 규칙**
- 두 브랜드 표는 **같은 격자**를 써야 한다. 열 수가 다르면 세로선이 어긋나 지저분해 보인다.
  멤버 피벗도 **열을 합집합**으로 맞춰 나란히 비교되게 한다(두 브랜드 멤버 구성이 동일).
- 값이 0인 칸은 `0` 대신 `—`. `—` 는 **정말 매출이 0인 오픈 국가**에만 나와야 한다.
- 숫자 열은 `tabular-nums` + `white-space:nowrap`.
- **각주는 최소화한다.** 서비스코인·쿠폰 예외국, 티켓번호, '대행사는 별도 발행' 같은
  내부 규칙은 적지 않는다. 파트너가 알아야 할 것만 남긴다.

### 계산식
```
매출액     = 실결제 + 쿠폰(지정국가) + 서비스코인(지정국가)   ← photoism_rules.py
             스내피즘은 전 국가 쿠폰 가산
현지 매출  = 매출액과 **같은 분자**를 현지통화로 (실결제만 쓰면 전액쿠폰 국가가 0으로 보임)
정산액     = 매출액 × RS율(소속사 / 대행사 각각)
수량       = floor(현지 분자 ÷ 현지 평균단가)   ← 두 브랜드 같은 공식, 부르는 이름만 다름
             📸 포토이즘 = 프레임수 (1건에 여러 장 가능: 23,673건 → 23,906장)
             📊 스내피즘 = 건수     (상품 1개 = 1건, 배수가 항상 1.0)
환율       = 서울외국환중개 매매기준율 · 정산 종료일 당일
             (주말·공휴일이면 직전 영업일) — update_rates.get_effective_date
             LAK·PEN 은 미고시 → 야후 USD 크로스레이트 (1÷LAK=X)×USD_KRW
             ※ 문서에는 **출처와 기준일만** 적고 크로스레이트는 내부에만 둔다
```
**검증식**: `현지 매출 × 환율 == 매출(KRW)` 이 모든 국가 행에서 성립해야 한다(오차 0.1% 내).
**반올림 지점을 한 곳으로 통일한다.** (현행 정산 페이지는 KPI는 float, 표는 행별 반올림이라 원 단위가 어긋남)

#### ★샘플 제작에서 실측으로 잡은 함정 (구현 시 반드시 반영)
1. **매출 기여 0원 거래는 제외한다** — 예외국 외 서비스코인·쿠폰 무료분.
   빼지 않으면 건수·프레임수만 부풀고 단가 평균도 내려간다.
   (한국 TREASURE 6월: 건수 11,697 → 11,480 / 단가 6,920 → **7,000**. 매출액은 불변 = 검증 포인트)
2. **단가 평균에서 0원 행 제외** — `AVG(NULLIF(상품 단가, 0))`. 위와 같은 원인.
3. **프레임수는 현지통화끼리 나눈다** — 원화 환산 후 현지 단가로 나누면 환율배수만큼 부풀어난다
   (실측 24,075 → 잘못 계산 시 1,553,437).
4. **멤버명 한/영 통합 필요** — 아사히↔ASAHI 등. 안 하면 같은 멤버가 두 열로 쪼개진다.
   Node 의 `name-mapping.json` 이 이 역할.
5. **`HARUTО` 의 О 가 키릴문자(U+041E)** — CMS 데이터 오염. 정규화 안 하면 별도 열이 생긴다.
6. **국가명이 브랜드마다 다르다** — 포토이즘 `한국` vs 스내피즘 `대한민국`. 한 문서에 실리므로 통일.
7. **오픈 국가 기준** — 현재는 '그 기간에 브랜드가 실제 영업한 국가 전체'(포토이즘 30개국,
   `config.json photoism.countries` 와 일치). 단 이건 **브랜드 영업 기준**이지 IP별 배포 기준이
   아니다. IP별 배포 국가를 관리하게 되면 그쪽으로 교체해야 정확하다.
8. **★스내피즘도 멤버별로 뽑힌다** — 초기 판단('프레임이 IP 단위라 멤버 구분 없음')은 **틀렸다.**
   `프레임 이름`·`컬렉션 이름` 은 IP 단위지만 **`상품 이름` 이 멤버명**이다.
   TREASURE 6월 기준 두 브랜드 멤버 구성이 11개로 완전히 같다(단체 `TREASURE` 포함).
9. **스내피즘 단가는 상품 형태마다 다르다** — 국가 하나로 평균 내면 형태 구성비에 휘둘린다.
   `{국가 × 상품 카테고리}` 로 쪼갤 것. (한국: 미니 4,898 / 와이드 4,918 /
   포토카드(IP) 10,645 / 포토카드(커스텀) 3,000 / 스티커(커스텀) 1,500)
10. **스내피즘 필터는 `프레임 이름`** 을 쓴다. `IP 이름` 으로 거르면 TREASURE 가 396행밖에
   안 잡힌다(실제 14,486행). 이 열은 상당수가 비어 있다.

## 단계 계획
1. **1단계 — 매핑 기반 구축**: 티켓 입력 → 후보 제시 → 승인·저장, 잔여 검증 0원 강제
2. **2단계 — 계산 엔진**: 매출·요율·프레임수·MG, 브랜드 2종 대응
3. **3단계 — PDF 생성**: HTML 템플릿 + Playwright, 국가별 비중 그래프
4. **4단계 — 발행 관리**: 스냅샷 잠금 · 정정본 재발행(사유 기록)
5. **5단계 — 메일 발송**: `sm_mail.py` 재사용

## 리스크
- **매핑 확정 작업량** — 포토이즘 464 타이틀 중 124개 미연결 + 모호 건, 스내피즘 84개 중 54개. 첫 달은 수작업 비중이 크다
- **요율 미입력** — 스내피즘 68% · 포토이즘 92%가 빈 값. 화면 입력으로 메우되 지라 역기입 여부는 미정
- **MG·파트너사 원천 부재** — 수기 입력으로 시작, 축적 후 마스터화
- **1:N 판단** — 한/영 동시출시 합산(정상) vs 회차 오합산(오류) 구분은 사람이 해야 함
